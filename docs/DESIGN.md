# 设计决策

## D1 工具的职责是判定，不是编辑

`scissors.py` 不产出任何新文本：不给"建议改成"，不给删后全文，只给判定、片段边界和阻断项。原因有两个。

第一，改写是过度生成的高发区。任何一个能改写的位置，模型都会顺手改。工具一旦有改写能力，就会被用来"顺便润色一下"。

第二，判定可以被机械验证，改写不能。给出删除片段的位置和字符数，对方能复核；给出一段"优化后"的文字，对方只能凭感觉。

## D2 用严格子序列作为可判定核心

不用相似度、不用编辑距离、不比对句数。判据只有一条：现文的字符序列是不是原文的子序列。

相似度会放过改写：把"值得注意"改成"要注意"，相似度 0.9，人的眼睛也容易放过，但那是新增。编辑距离会奖励"改得少"，仍然允许改。子序列是唯一同时排除新增、改写、替换、重排的判据，而且判定是 O(n) 的。

代价是严格：改一个逗号也过不了。这是设计意图。要改标点就明说这是编辑而不是删减，走另一条路径。

## D3 对齐算法：两指针判真，SequenceMatcher 定界

子序列判定用两指针，这是充要判据，不会误判。

删除片段的划分用 `difflib.SequenceMatcher`，因为它优先匹配最长公共块，能把"删掉列表里的一条"还原成整行删除；两指针的贪心对齐会在字符层面切出半个词，造成假的"非完整单元"阻断。

SequenceMatcher 的划分不参与判定，只参与报告：拿它还原出的现文必须与真实现文逐字相等，否则退回两指针的结果。这样即使 Ratcliff/Obershelp 找到的不是最长对齐，也不会污染判定结论。

一个附带事实：子序列的删除片段集合不唯一。删清单里的第二项，"删除第二行"和"删除第二行加它后面的换行"都是合法对齐。工具给的是其中一种，报告里的边界判断要容得下这种歧义，见 D4。

## D4 单元边界判据

删除单位只有四种：完整句子、完整列表项、完整段落、整节。这些单位之间没有统一的分隔符，所以判据分两条，满足其一即算对齐：

- 句子边界：片段前一个字符和片段最后一个字符都是句末标点或换行
- 块边界：片段整行整行地删，两端可以各带一个换行。标题、列表项、表格行、整行代码都靠这条

两端换行允许在片段内部或外部，因为空行归属天然有歧义，硬判会产生大量误报。

判不了的一律标 `partial` 并阻断。放行开关 `--allow-partial-unit` 存在，但默认关闭：一个能随手关掉的开关，等于没有这条约束。

## D5 保护内容一律硬阻断，不做"提示"

数字、单位、链接、代码、引用、警告、定义、出处、用户点名项，出现在删除片段里就阻断，退出码 2。

不做"只是提醒一下"：提醒会被忽略，阻断不会。宁可交付一份删得不够的稿子，也不交付一份丢了数据的稿子。

## D6 双信号，防的是过度删除

只靠词典命中就删，会删掉人写的正常过渡。所以候选需要两个独立信号：命中废话语料，且信息密度低或与前文重复。

例外是四类强套话：祈求式收尾、时代背景铺陈、交代本文结构、装饰符号。这四类删掉后信息量为零，单信号即可。

这个设计在测试里有对应用例：`report_clean.md` 是一份正常技术说明，含"由此可见"，工具必须产出零个可删候选。假阳性控制住不了，工具就会被当成"建议全删"的授权，反而助长过度删除。

## D7 含数据的弱套话：整句保留

最常见的误删形态是"值得注意的是，本月活跃用户为 12,480 人"。

可删的只有前缀四个字，但前缀不是完整单元，删了会留残句；整句删掉又丢数据。按单元完整性判据，正确动作是整句保留。

所以 `scan` 对这类句子给的不是"删除"，而是"整句保留（按单元完整性不得只删前缀）"，并在 `blocked_by` 里写明含哪些保护内容。这条是 D4 与 D5 交汇处的必然结论，不是特例补丁。

## D8 重复总结用包含度，不用 Jaccard

判断"总结段是否重述前文"，用字符二元组的包含度（交集除以较小集合），不用 Jaccard。

总结段通常是前文的超集或浓缩，Jaccard 会因为它更长而给出偏低的重合度，把明显的重复总结判成不重复。包含度衡量"这段有多少内容在前文出现过"，与实际语义对齐。

阈值默认 0.45，可用 `--min-overlap` 调。只在段首命中总结标记时才算，避免把正常承接判成重复。

## D9 代码门禁用 numstat，不解析 diff 正文

`git diff --numstat` 直接给每个文件的增删行数，是稳定的机器接口；解析 diff 正文要处理颜色、上下文、二进制、重命名，脆弱且容易看错。

新增行数大于零即失败。理由是：一次"减法"改动里出现新增行，说明混了别的东西。要么承认这是普通改动，要么拆成两次提交。这两条路都比让它悄悄混过去好。

测试通过与否交给 `--test-cmd`，由调用方给命令。工具不去猜项目用什么测试框架。

## D10 不做的事

- 不调用任何模型。判定必须是离线可复现的。
- 不装第三方依赖。标准库加 git，任何有 Python 的机器能跑。
- 不判断语义相关性。"这段与用户要求是否无关"需要读用户原话，属于 skill 的职责，不是工具的。
- 不自动删除。工具只出报告，动手的是调用方。
- 不做 web 界面。命令行加 JSON 足够接 CI。
- 不提供"一键清理"。一键清理等于把判据外包给正则。

## 已知的判不了

- `scan` 的词典是人工维护的，新式套话不在里面就是漏报。漏报可以接受，误报会助长过度删除，所以词典只收判据明确的说法。
- `scan` 会把作者写的正常过渡标成候选。这是词典法的固有误差，靠双信号和人工复核压住。
- 单元边界是启发式。表格行、代码块内的行、跨段的列表，边界判定可能偏严，只会多阻断，不会少阻断。
- 是否"承担必要衔接"，工具完全判不了。这条只能人工判，且默认保留。
