# 代码减法

只删没人用的东西。判定靠证据，不靠直觉。

## 三问

任一条答不上来就别删：现在有人用它吗？删了谁会挂？加回来要多久？

## 候选

- 只有一个实现的接口、抽象基类、工厂、策略
- 未使用的参数、配置项、功能开关、环境变量
- 复述式注释：`# 返回结果`、`# 循环处理`、`# 初始化`
- 被注释掉的旧代码
- 为将来预留的钩子、空实现、TODO 占位、`NotImplementedError` 的占位分支
- 无谓防御：内部调用处的重复校验、不可能为 None 的判空
- 只做一次转手的中间变量与包装函数
- 日志噪音：每个步骤都打日志
- 多余依赖：为了一个函数引入一整个库
- 文档里的营销段落与自夸

## 不删

删了会出事的，一律不碰：

- 错误处理与边界校验，尤其 IO、网络、权限、金额、并发
- 安全相关：鉴权、转义、限流、脱敏
- 可观测性埋点与关键日志
- 公开契约：API、schema、CLI 参数、文件格式。要改属于破坏性变更，单独提交并写迁移说明
- 许可证头、致谢、法律声明
- 兼容层。看起来丑，但外部还有人在用
- 测试。测试看着冗余往往是覆盖率撑着的

## 证据要求

"看起来没人用"不是证据。给出命令与输出：

```
git grep -n "符号名" -- ':!docs'
```

零命中才算没人用。只在本文件出现一次的，是私有实现，可以直接删。被配置或反射调用的（字符串里出现），不算零命中。

## 门禁

```
python tools/scissors.py code --repo . --test-cmd "你的测试命令"
```

只有删除行，且测试通过，才算减法。出现新增行就说明这次改动里混了东西：要么承认它是正常改动，要么拆成两次提交。工具用法见 scissorhands-gate。

## 台账

工程型交付要给删除台账，一行一条：

| 删除 | 理由 | 证据 |
| --- | --- | --- |
| `RetryPolicy` 接口 | 只有 `ExponentialRetry` 一个实现 | grep 到 1 处定义、0 处其他引用 |
| `--legacy` 开关 | 无调用方，配置里也没出现过 | grep 到 0 处使用 |

台账里不写"顺手优化""更清晰"。只说删了什么、凭什么。

## 常见失败

- 删了抽象层，同时把调用点也改了。这是重构，不是减法，得走正常评审。
- 为了让测试通过去改测试断言。测试是证据，不是障碍。
- 删掉 `if not path.exists()`，因为"上游已经检查过"。上游是谁、哪个提交检查的，拿不出来就是删错。
- 删完留下一个空文件或空目录。空壳也是新增。
