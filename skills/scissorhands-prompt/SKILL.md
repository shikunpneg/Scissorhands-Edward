# 指令减法

规则多不等于听话。规则之间打架，模型会挑一条执行，挑哪条你控制不了。

## 唯一判据

删掉这条规则，模型行为变不变？

- 不变：这条规则在浪费上下文，删。
- 变差：回填，并把这个失败场景写成用例。
- 说不清：说明这条规则从来没有被验证过。先补用例，再判断。

没有用例就没有判据。不许凭"这条看着很重要"保留，也不许凭"这条看着啰嗦"删除。

## 候选

- 同一约束换三种说法写三遍：字数限制、格式要求、禁止事项最常见。
- 互相冲突的规则：A 说必须简短，B 说要列全所有字段。
- 无判据的强调：非常重要、务必、一定要、绝对不能。强调不产生行为，判据才产生行为。
- 能被工具签名或类型推断的说明：参数范围、默认值、是否必填。这些写进 schema。
- 膨胀的 few-shot：保留最难的两个，删掉模型一遍就能做对的。
- 与任务无关的角色设定与背景故事。
- 长串注意事项罗列。改成让工具报错，报错比叮嘱有效。
- 已过期的历史上下文：上一轮的中间结果、已经失效的临时约定。
- 重复的描述符：同一个工具的 description 在系统提示里又抄一遍。

## 保

- 术语定义。同一个词在这里是什么意思，必须留。
- 输出 schema 与格式契约。
- 安全边界：什么绝对不能做。
- 失败处理：出错时该报错还是重试。
- 与用户明确要求对应的规则。

## 消融台账

工程型交付，每次删都要有这张表：

| 规则 | 删后的验证用例 | 结果 | 决定 |
| --- | --- | --- | --- |
| "回答不要超过 200 字" | 三条例行长问题 | 长度 320、410、380 | 回填，改写为"先给结论，细节按需" |
| "必须使用中文标点" | 中英混排输入 | 输出仍混用英文标点 | 回填 |
| "工具调用前先解释意图" | 简单查文件 | 行为无变化 | 删除 |

台账里不写"更简洁""更清晰"，只写用例结果。

## 上下文预算

按 token 算，不按条数算。删之前先测：这条规则占多少 token，删掉能换回多少个可用的示例。一条 200 token 的规则换两个高价值示例，通常划算；换零个，就不划算。

上下文超预算时的裁剪顺序：过期历史、重复规则、可推断的说明、简单 few-shot、弱判据强调。术语定义与安全边界放最后。

## 常见失败

- 为了压字数把规则合并成一句长句，模型解析难度反而更高。
- 删了"注意"类提醒，却没让工具给出明确报错，于是错误率上升，回头又加回来。
- 只看总字数下降，不看用例结果。字数降了、行为坏了，属于变差。
